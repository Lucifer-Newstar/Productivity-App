# v0.1.1 deterministic Core Today routing contract

**Status:** FROZEN BEFORE IMPLEMENTATION
**Contract version:** `1.0`
**Governing decision:** [AI-ADR-019](adrs/AI-ADR-019-DETERMINISTIC-CORE-TODAY-ROUTING.md)

## Purpose

This contract separates trusted routing from untrusted generation. It does not implement routing. It defines the only v0.1.1 intent, tool, evidence and model-output boundary that future implementation may use.

## Deterministic route

Trusted Kaizen code constructs `DeterministicTodayRouteV1` only for the fixed Home focus request:

```ts
interface DeterministicTodayRouteV1 {
  schemaVersion: "1.0";
  routeId: string;
  capability: "core.today.interpret";
  intent: "focus-today";
  selectedBy: "kaizen-deterministic-router";
  tool: {
    name: "get_today";
    version: "1.0";
    arguments: {
      localDate: string;
      includeCompleted: false;
      maximumItems: number; // 1..100
    };
  };
  evidenceContract: "core.today@1.0";
  allowedDomains: ["core"];
  modelToolAccess: "none";
}
```

There is no free-text route classifier, fuzzy domain selection or model fallback. An unsupported intent returns a typed unsupported result to the UI without calling a provider.

## Tool execution

The route chooses exactly `get_today@1.0`. Existing gateway/session and Domain Bridge controls still apply:

1. authenticate the paired session;
2. validate the route schema and fixed capability;
3. issue one correlated `get_today@1.0` request;
4. validate arguments and the returned `core.today@1.0` snapshot;
5. reject stale, invalid, oversized or mismatched evidence;
6. create the interpreter request only after validation.

The model never sees a tool definition and never receives a tool-result continuation round.

## Interpreter request

`TodayInterpreterRequestV1` contains the route, one validated `DomainSnapshot<TodayContextV1>` and an explicit provider policy:

```ts
providerPolicy: {
  tools: "forbidden";
  additionalRetrieval: "forbidden";
  memory: "forbidden";
  writes: "forbidden";
}
```

Only the minimum fields already allowed by `core.today@1.0` may enter evidence. Notes, raw localStorage, Health, other domain records, memories, credentials and hidden settings remain excluded. User-authored titles and imported text are serialized as untrusted data, never instructions.

## Interpreter response

The provider must return one structured `recommendation` with:

- bounded `title` and `summary`;
- bounded rationale items labeled as fact, deterministic result, inference or assumption;
- confidence in `[0, 1]`;
- explicit uncertainty and assumptions arrays;
- source IDs drawn only from supplied evidence.

Additional properties are rejected. In particular, the response has no command, proposal, tool-call, automation, memory or arbitrary-domain field.

## Precedence and grounding

- A supplied deterministic Next Action outranks model preference.
- The model may explain that deterministic result or disclose why evidence is insufficient; it may not silently replace it.
- Every factual or deterministic rationale claim cites supplied source IDs.
- Fabricated, missing or cross-snapshot IDs invalidate the response.
- When evidence is empty, stale, contradictory or insufficient, uncertainty is mandatory and confidence must remain bounded by the evaluation rubric.
- The engine and browser retain final source verification before rendering.

## Failure contract

| Condition | Required outcome |
|---|---|
| Intent is not fixed `focus-today` | Fail closed; no provider request |
| Route requests another tool/domain | Reject route |
| Snapshot contract/version mismatch | Reject evidence |
| Snapshot is stale during processing | Mark stale/fail; do not present as current |
| Provider emits any tool call | Reject response; no tool execution |
| Invalid JSON/schema | One bounded repair may be evaluated later; otherwise fail safely |
| Unknown source ID | Reject response |
| Deterministic precedence violated | Reject response |
| Write/action/automation shape appears | Reject response |
| Provider unavailable | Preserve deterministic Home behavior |

## Versioning

Any change to the capability, intent, tool, evidence contract, allowed domain, model authority or output shape requires:

1. a contract version change;
2. ADR review if authority/scope changes;
3. frozen evaluation updates before implementation;
4. synthetic and adversarial regression fixtures;
5. synchronized security, ledger, roadmap and report updates.

Machine-readable types and JSON Schemas live in `ai/src/contracts/interpreter.ts`.
